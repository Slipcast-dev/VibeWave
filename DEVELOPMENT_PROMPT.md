# Промт: разработка VibeWave от идеи до релиза

Ниже — самостоятельное задание для ИИ-разработчика. Его можно скопировать целиком в новый чат вместе с доступом к проекту. Это спецификация процесса и результата, а не заявление, что все этапы публичного выпуска уже выполнены.

---

## Роль и цель

Ты — ведущий разработчик нативных macOS-приложений. Проведи полный цикл создания **VibeWave**: анализ → требования → дизайн → архитектура → реализация → проверки → исправления → документация → локальный релиз → подготовка публичного выпуска → сопровождение.

Результат — лёгкий законченный аудиоплеер для локальных **MP3 и FLAC**, с вручную создаваемыми плейлистами, отдельной временной очередью и интерфейсом в стиле **Windows 95**. Минимализм — обязательное свойство продукта.

Если проект уже существует, сначала изучи его и продолжи разработку от текущего состояния. Не создавай заново работающие части и не заменяй репозиторий шаблоном. При конфликте текста с более поздними явными требованиями владельца выполняй актуальные требования, сохраняя рабочие данные.

Общайся на русском языке. Комментарии к сложной логике и документация — на русском. Названия типов, методов и файлов должны следовать соглашениям Swift.

## Правила работы

1. Изучи инструкции проекта, структуру, `Package.swift`, `VERSION`, Git status и существующие документы до изменений.
2. Не выдавай предположения за факты. Проверяй сомнительные API и требования выпуска по официальной документации Apple.
3. Задавай вопросы только при существенной неопределённости. Обычные обратимые действия выполняй самостоятельно в пределах задания.
4. До потенциально разрушительных изменений создай резервную копию или подготовь проверяемый dry-run. Не трогай посторонние файлы и чужие изменения.
5. Разделяй пользовательскую библиотеку, исходники и производные сборки.
6. Не хардкодь секреты, не записывай их в документацию или логи. Учётные данные подписи используй через защищённые механизмы.
7. Не отключай SIP, Gatekeeper и другие системные защиты ради запуска.
8. Не выдумывай результаты тестов, прослушивания, измерений, подписи и нотариализации.
9. Держи владельца в курсе важных результатов. Доводи каждый разрешённый этап до конкретного проверяемого результата.
10. Отправка кода, загрузка на внешние сервисы и публикация требуют соответствующего явного поручения. Подготовка локального релиза сама по себе не разрешает публичную публикацию.

Подготовь короткое описание продукта, перечень функций, ограничения и критерии приёмки. Не добавляй эквалайзер, обложки, социальные функции и другие необязательные панели.

**Результат этапа:** согласованное понимание задачи и компактное ТЗ.

## Этап 2. Требования к поведению

### Воспроизведение

Реализуй:

- воспроизведение и паузу;
- предыдущий/следующий трек;
- перемотку и громкость;
- текущую позицию и длительность;
- ручной порядок перетаскиванием мышью и случайный режим без повторов в одном проходе;
- автоматический переход к следующему треку и остановку после конца очереди;
- понятную обработку недоступного, повреждённого или неподдерживаемого файла.

Открытие нового трека должно освобождать ресурсы прежнего. Пауза должна останавливать ненужные периодические обновления. Не обещай gapless, bit-perfect и другие специальные аудиорежимы без реализации и проверки.

### Очередь и плейлисты

Раздели два вида коллекций:

1. **Временная очередь:** музыка вне плейлистов, в памяти до завершения приложения.
2. **Ручные плейлисты:** пользовательские названия и порядок, сохранённые между запусками.

Ни при запуске, ни при открытии, ни при обычном добавлении музыки автоматически не создаётся плейлист.

Матрица действий:

| Действие | Ожидаемое поведение |
|---|---|
| Добавление при показе очереди | Добавить в очередь |
| Добавление при выбранном ручном плейлисте | Добавить именно туда |
| Открытие через Finder/Dock | Переключить просмотр на очередь и открыть музыку вне плейлистов |
| Перетаскивание на название плейлиста | Добавить непосредственно в него |
| Перестановка внутри раздела | Изменить порядок |
| Перенос между ручными плейлистами | Переместить запись |
| Добавление из очереди в плейлист | Добавить запись, сохранив очередь |
| Перенос из плейлиста в очередь | Добавить в очередь, сохранив исходный плейлист |
| Удаление записи/плейлиста | Не удалять аудиофайл с диска |
| Закрытие окна | Сохранить процесс и временную очередь |
| Завершение приложения | Завершить сеанс; сохранить ручные плейлисты |

Исключай дубликаты внутри раздела по нормализованному файловому URL. Конфликт дублей в получателе не должен приводить к удалению исходной записи. Переключение просмотра не должно само по себе менять текущую музыку.

**Результат этапа:** проверяемые функциональные и нефункциональные требования.

## Этап 3. Дизайн и макет

Создай минималистичный интерфейс в стиле Windows 95:

- квадратные кнопки с объёмными гранями и эффектом нажатия;
- вдавленные поля и чёткие рамки;
- компактная таблица названия, формата и длительности с читаемым шрифтом;
- изменение ширины каждого столбца мышью с сохранением и сбросом двойным щелчком;
- постоянный список музыки вне плейлистов, видимый при выборе любого плейлиста;
- прямоугольные бегунки перемотки и громкости;
- слева ручные плейлисты, справа треки, снизу воспроизведение;
- кнопка добавления файлов снизу слева рядом с выбором темы;
- отсутствие повторяющейся большой подписи «Открытые файлы»;
- небольшая доступная кнопка с нотой для возврата к очереди, с понятной подсказкой.

Три палитры:

1. **Windows 95:** серые панели, белые списки, тёмно-синие заголовок и выделение.
2. **Светлая:** чёрно-белая.
3. **Тёмная:** тёмные поверхности с фиолетовыми элементами.

Сохраняй выбор темы. У выделенного текста должен оставаться достаточный контраст во всех палитрах. Не заменяй доступные элементы имитацией без клавиатурного управления.

Разработай иконку: узнаваемая фиолетовая волна на тёмной скруглённой плитке. Сохрани исходник, прозрачность и варианты для Dock/Finder. Проверь видимость на маленьком размере.

Покажи макет или экспорт тестового интерфейса. Отличай макет от снимка работающего приложения и не подставляй в него приватную музыку пользователя.

**Результат этапа:** согласованный экран, палитры, иконка и описание взаимодействий.

## Этап 4. Архитектура

Используй простую модульную архитектуру:

- `VibeWaveCore`: модели, хранилище и операции над списками;
- `PlayerModel`: наблюдаемое состояние, импорт и воспроизведение;
- SwiftUI-представления: экран, строки, темы и ретро-контролы;
- узкая AppKit-часть: приложение, меню, окно, системные события;
- отдельные тесты, аудиофикстуры и сценарии сборки.

Определи:

- `Track`: идентификатор, URL, необязательная закладка, название и длительность;
- `Playlist`: идентификатор, название, упорядоченные треки;
- payload перетаскивания: идентификаторы исходного раздела и трека;
- `nil` в идентификаторе раздела как временную очередь;
- JSON только для ручных плейлистов;
- независимость текущего воспроизведения от показанного раздела.

Следуй KISS и DRY. Не вводи базу данных, сервер и сложные абстракции без необходимости.

**Результат этапа:** структура файлов, границы ответственности и потоки данных.

## Этап 6. Ядро, хранение и миграция

Реализуй Codable-модели, загрузку и атомарное сохранение JSON.

Требования:

- отсутствие файла библиотеки — нормальный первый запуск;
- первый запуск не создаёт плейлист;
- повреждённый JSON вызывает понятную ошибку и не перезаписывается молча;
- пустое название плейлиста отклоняется;
- исходная музыка не копируется и не удаляется;
- библиотека хранится в Application Support вне исходников;
- временная очередь не становится скрытым сохранённым плейлистом;
- миграция прежней библиотеки, если нужна, не изменяет её исходный файл.

Для существующего VibeWave учти переход из `Tiho/library.json` в `VibeWave/library.json`. Новое изменение схемы должно сопровождаться явным планом совместимости и отката.

**Результат этапа:** работающая библиотека и проверки сохранности данных.

## Этап 7. Импорт и воспроизведение

Проверь MP3 и FLAC настоящим декодером, а не только расширением.

- Выполняй длительную проверку файлов в фоне.
- Меняй наблюдаемое состояние на главном потоке.
- Фиксируй назначение импорта до начала фоновой работы.
- Сохраняй порядок входных файлов.
- Ограничь одновременный импорт, чтобы не терять результаты.
- Обрабатывай частичный успех: исправные файлы добавляются, ошибки перечисляются с причиной.
- Не считай отсутствие security-scoped закладки фатальным для локальной сборки без App Sandbox, если обычный URL доступен.
- Корректно открывай и закрывай security-scoped доступ, когда он предоставлен.
- Освобождай проигрыватель и таймеры при остановке.

При перестановке треков обновляй будущую очередь без прерывания текущего звука. Не смешивай выбранный пользователем список и источник уже начатого воспроизведения.

**Результат этапа:** реальное воспроизведение и устойчивый импорт.

## Этап 8. Перетаскивание

Поддержи внешние файлы и внутренние строки отдельно.

Не полагайся только на широкий фильтр совместимости SwiftUI. Для внутреннего типа проверь точный идентификатор в `registeredTypeIdentifiers`, а для внешних файлов используй файловые URL. Зарегистрируй внутренний UTI в свойствах приложения.

Проверь весь путь:

```text
внешний NSItemProvider → распознавание → URL → декодирование → нужный раздел
внутренний NSItemProvider → payload → перестановка/перенос
```

Тест, которому сразу передали URL, не заменяет проверку настоящего provider. Отдельно проверь несколько асинхронных результатов, перестановку в конец и ситуацию, когда очередь открыта при выбранном ранее плейлисте.

**Результат этапа:** работающие внешние и внутренние переносы с регрессионными проверками.

Сохрани стандартные меню, `⌘O`, `⌘W`, `⌘M`, `⌘Q` и редактирование названий. Свяжи открытие MP3/FLAC через Finder/Dock с временной очередью. Установи иконку и в ресурсы bundle, и в работающий AppKit/Dock.

## Этап 14. Публичный релиз

Этот этап выполняется отдельно от локальной сборки, когда известны канал распространения, архитектуры и доступы владельца.

До публикации:

1. Проверь актуальные требования Apple по официальной документации.
2. Подготовь Developer ID-подпись, Hardened Runtime и минимально необходимые entitlements.
3. Используй Keychain или иной согласованный защищённый способ работы с учётными данными.
4. Подготовь и проверь каждую заявленную архитектуру; universal binary не считай готовым автоматически.
5. Создай отдельный распространяемый артефакт, не смешивая его с обычной ad hoc сборкой.
6. Выполни разрешённую нотариализацию, проверь журнал и результат.
7. Прикрепи ticket и проверь окончательный пакет.
8. Проверь его на другом Mac или чистом пользовательском окружении.
9. Подготовь release notes, контрольную сумму, перечень ограничений и план отката.
10. Выполни публикацию только в явно порученный канал.

Если нет сертификата, доступа, подходящей машины или разрешения на публикацию, заверши все независимые локальные работы, подготовь конкретный релизный план и точно укажи оставшийся шаг. Не обходи защиту и не объявляй публичный выпуск состоявшимся.

**Результат этапа:** либо действительно проверенный и опубликованный релиз в разрешённом канале, либо готовый локальный результат с чётко обозначенной границей до публикации.

## Этап 15. Сопровождение

После выпуска:

- фиксируй воспроизводимые ошибки и версии окружения;
- сначала добавляй проверку дефекта, затем исправление;
- сохраняй совместимость библиотеки или готовь миграцию и откат;
- обновляй версию, CHANGELOG и документацию при изменении поведения;
- повторяй релизные проверки для изменённых артефактов;
- не добавляй необязательные функции без запроса владельца.

## Критерии завершения задания

- [ ] MP3 и FLAC действительно открываются и проигрываются.
- [ ] Плейлисты создаются только вручную.
- [ ] Обычная музыка доступна вне плейлистов.
- [ ] Удаление записей не удаляет исходные файлы.
- [ ] Перетаскивание из Finder и переносы внутри плеера работают раздельно.
- [ ] Все три темы читаемы и сохраняются.
- [ ] Столбцы изменяются мышью; формат и время читаемы.
- [ ] Очередь видна при выбранном плейлисте.
- [ ] Ручной перенос включает порядок по списку, а случайные переходы сохраняют одну последовательность.
- [ ] Кнопка добавления находится рядом с выбором темы.
- [ ] Нет повторяющейся бессмысленной подписи очереди.
- [ ] Ретро-кнопки окна выполняют настоящие действия.
- [ ] Иконка видна в ресурсах и работающем приложении.
- [ ] Сборка воспроизводится, её подпись проверяется.
- [ ] Выполнены уместные автоматические и ручные проверки.
- [ ] Непроверенные платформы и сценарии названы явно.
- [ ] Документация соответствует текущему коду.
- [ ] Локальный Git не содержит сборок, кешей и секретов.
- [ ] Локальный выпуск отделён от публичной публикации.
- [ ] Для релиза предусмотрен возврат к предыдущей версии и совместимым данным.

## Формат итогового отчёта

Дай короткий отчёт на русском:

1. Что готово и каково итоговое поведение.
2. Где находятся проект, приложение и полная документация.
3. Какие проверки реально выполнены и что не проверено.
4. Ветка и коммит, если работа велась в Git.
5. Статус выпуска: локальная сборка, подготовка публичного релиза или выполненная публикация.
6. Единственный следующий необходимый шаг, если он зависит от владельца.

Не подменяй результат планом и не называй макет работающим приложением. Каждый завершённый этап должен подтверждаться файлом, сборкой, результатом проверки или реально выполненным действием.
